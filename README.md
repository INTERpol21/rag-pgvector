# rag-pgvector

> Исходный код проекта закрыт — здесь его описание: архитектура, решения и результаты. Код покажу по запросу: Telegram [@interpol2121](https://t.me/interpol2121).

Поиск по базе знаний с честными цитатами: два конвейера — ingest (нарезка →
векторизация → запись) и query (векторизация вопроса → гибридный ретривал →
опциональный реранкер → обоснованный ответ со сносками `[n]`). Гибридный
ретривал сплавляет векторную ногу и ключевую (BM25 в памяти, Postgres FTS в
pgvector) взвешенным слиянием (по умолчанию convex — по нормализованным скорам,
альтернатива — Reciprocal Rank Fusion); принцип local-first поднимает твои
данные выше веб-источников. По умолчанию всё работает офлайн — без базы и без
ключей.

## Место в платформе

```mermaid
flowchart LR
    CONS["llm-platform-console<br/>(Knowledge)"] --> RAG["rag-pgvector :8081"]
    ORCH["agent-orchestrator<br/>(rag_search)"] --> RAG
    RAG -->|"эмбеддинги"| GW["llm-gateway"]
    RAG --> PG[("Postgres + pgvector<br/>documents · chunks")]
    DROP[("./dropbox<br/>папка-коннектор")] --> RAG
```

Консоль загружает и ищет документы через этот сервис; исследовательский агент
берёт отсюда локальные улики; эмбеддинги идут через шлюз — расход виден в
одном журнале.

## Запуск всей платформы

Вся платформа — четыре бэкенда, консоль, Postgres и Redis — поднимается одной
командой из соседнего репозитория
[llm-platform-console](https://github.com/INTERpol21/llm-platform-console),
который держит зонтичный `docker-compose.yml`. Пять репозиториев должны лежать
рядом в одной папке:

```bash
cd ../llm-platform-console
cp .env.example .env
docker compose up --build     # консоль на http://localhost:8080
```

Всё работает офлайн на мок-моделях без единого API-ключа; ключ авторизации по
умолчанию — `demo-key`. Главный план сборки, схема платформы и экскурсия — в
README консоли.

## Быстрый старт (этот сервис отдельно)

```bash
make install-dev   # make install — то же без dev-инструментов
make run           # uvicorn на :8081, офлайн: память + хэш-эмбеддер + мок-LLM

# загрузить документ и спросить
curl -s -H "Authorization: Bearer demo-key" -H "Content-Type: application/json" \
  -d '{"documents":[{"id":"note","title":"RRF","text":"RRF объединяет ранжирования..."}]}' \
  http://localhost:8081/v1/ingest
curl -s -H "Authorization: Bearer demo-key" -H "Content-Type: application/json" \
  -d '{"question":"что такое RRF?"}' http://localhost:8081/v1/query
```

## API

`/v1` — клиентский API; вне версии два операционных маршрута: `/healthz`
(без ключа) и `/metrics` (с ключом). Весь `/v1` — под пер-ключевым
rate-limit'ом (`RAG_RATE_LIMIT_RPM`, 429 + `Retry-After`); операционные
маршруты — вне бюджета.

| Эндпоинт | Что делает |
|---|---|
| `POST /v1/ingest` | JSON-документы: нарезка → эмбеддинг → запись. Дедуп по хэшу заголовка и текста в пределах коллекции: документ со своим `id` при том же содержимом пропускается (`unchanged`); документ без `id`, чьё содержимое в коллекции уже есть, не пишется второй раз (`duplicate`, в ответе id существующего). Исход по каждому документу — в `documents[]` ответа. id, уже живущий в другой коллекции, — 409 (документ не переезжает) |
| `POST /v1/ingest/file` | Загрузка файла md/txt/pdf/docx (до 10 МБ), разбор в worker-потоке с бюджетами (размер после распаковки, время, не больше двух разборов разом); файл сверх бюджета — 413. Файл идёт без `id`, так что повторная загрузка того же файла в ту же коллекцию — `duplicate`, а не копия; изменённый файл — новый документ рядом со старым |
| `POST /v1/query` | Вопрос → гибридный ретривал → ответ со сносками `[n]` и уликами; каждый найденный фрагмент в `retrieved[]` несёт полный текст чанка (`text`, дословно; потолок 8000 символов — срез помечен `text_truncated`), а не только процитированные 200-символьные выдержки. `best_vector_score` — сырой косинус ближайшего фрагмента в области поиска, `low_coverage` — мягкий флаг «в корпусе, скорее всего, нет ответа» (косинус ниже порога эмбеддера; см. `LOW_COVERAGE_COSINE`) |
| `POST /v1/retrieve` | Только ретривал, без синтеза ответа: до двух вариантов настроек (режим/слияние/веса/локальный приоритет/реранкер) над ОДНИМ пулом кандидатов, опц. `explain` — вклад каждой ноги в итоговый скор; каждый фрагмент несёт тот же `text`, что в `/v1/query`, ответ — те же `best_vector_score`/`low_coverage` (одни на все варианты: векторная нога общая); живую конфигурацию не меняет. Каждый вариант стоит один токен rate-limit'а (в зонтичном стеке бюджет общий с research — один `PLATFORM_KEY`) |
| `GET /v1/documents` | Страница списка документов (новые первыми) с числом чанков |
| `GET /v1/documents/{id}` | Документ и страница его фрагментов по порядку (`limit` ≤ 100, `offset`); id с косой чертой — тоже работает |
| `DELETE /v1/documents/{id}` | Удаление документа с чанками; id с косой чертой — тоже работает |
| `POST /v1/collections` | Новая пустая коллекция (слаг `id` + `name`); 409 с машиночитаемым `code`: `collection_exists` — id занят, `collection_limit` — достигнут потолок `RAG_MAX_COLLECTIONS` |
| `GET /v1/collections` | Все коллекции с числом документов, флагом `is_default` и потолком `max_collections` |
| `DELETE /v1/collections/{id}` | Удаление ПУСТОЙ коллекции; 404 — нет такой; 409 с `code`: `collection_not_empty` (сначала удалите её документы) или `collection_default` (дефолтная неудаляема) |
| `GET /v1/stats` | Бэкенды и счётчики корпуса; `reindex_pending` — векторы корпуса записаны другим эмбеддером, и `/v1/query` пока ищет только по ключевым словам |
| `GET /v1/config/hybrid-weights` | Текущий баланс гибридного слияния (vector/keyword) |
| `PUT /v1/config/hybrid-weights` | Перенастроить баланс на лету — переживает рестарт; отвергает значения, которые ломают ранжирование (отрицательные, оба нуля, inf/nan). Каждое изменение пишется в журнал в той же транзакции; не удалось записать — 503 `config_audit_unavailable`, ничего не изменено; тот же баланс повторно — no-op без записи |
| `GET /v1/config/changes` | Журнал изменений настроек (веса гибрида): кто, когда, было → стало; курсорная пагинация (`limit` ≤ 100, `cursor`, фильтр `setting`); свой ключ виден 8-символьным префиксом дайджеста, чужой — только «другой ключ» |
| `GET /v1/config/retrieval` | Действующие настройки ретривала: режим, правило слияния, веса, вес локального приоритета, пул, реранкер, RRF k, порог `low_coverage_cosine` (null — флаг выключен) |
| `GET /metrics` | Прометеевский текст (вне `/v1`, ключ обязателен): сканы вотчера, запросы с/без цитат, retrieve-запросы по числу вариантов и `explain`, ingest indexed/dedup, создания/удаления коллекций по исходу, изменения настроек по исходу (записано / no-op / журнал недоступен) |

`sources` в запросе ограничивает поиск ярусами происхождения (`local` /
`other` / `web`) — строгий режим «только мои данные». Это SQL-предикат
внутри обеих ног ретривала (включая ANN-кандидатный CTE), а не пост-фильтр
по пулу кандидатов — гарантия точная, а не статистическая. `sources: []` и
отсутствие поля — разные запросы: отсутствие = без фильтра, пустой список =
ни один источник не подходит.

## Как это устроено

- **Гибрид через слияние `FUSION`:** каждая нога отдаёт пул кандидатов
  (`max(top_k*4, 20)` — ровно один раз), слияние по умолчанию convex
  (min-max-нормализованные скоры ног), `FUSION=rrf` — Reciprocal Rank Fusion
  (k=60); ничьи детерминированно бьются по id чанка.
- **HNSW по-настоящему:** ANN-скан живёт в отдельном `MATERIALIZED`
  подзапросе (единственная форма, которую индекс умеет обслуживать),
  детерминизм — во внешней сортировке; `hnsw.ef_search` пинится на запрос.
  При source-фильтре скан дополнительно включает
  `hnsw.iterative_scan = relaxed_order` (pgvector 0.8+): предфильтрованный
  обход графа отбрасывает кандидатов на ходу, и без этой настройки
  селективный фильтр возвращает меньше строк, чем просили. Ключевая нога —
  генерируемый `tsvector` на конфиге `russian` (кириллица через
  russian_stem, латиница через english_stem) — те же стеммеры, что в
  офлайн-ноге BM25.
- **Ключевая нога, которая реально находит:** раньше tsquery склеивался
  через AND — вопрос из семи слов матчил только чанк со всеми семью, и на
  живой базе ключевая нога **не находила ничего для 71% вопросов** золотого
  набора (hit_rate 0.29 — ниже случайных 0.38), а гибрид молча вырождался в
  чисто векторный поиск. In-memory нога (BM25) этого не показывала — эвал
  мерил не тот ранжировщик, что обслуживает трафик. Теперь запрос
  OR-склеивается из лексем того же анализатора: чанк, покрывающий больше
  вопроса, ранжируется выше (`ts_rank_cd`), hit_rate ключевой ноги 0.86, а
  гибрид (0.88) обгоняет обе ноги — первое измеренное оправдание гибридного
  поиска в этом репозитории.
- **Один токенизатор на весь сервис:** индекс многоязычный (Snowball-стемминг
  с обеих сторон), но слои над ретривалом — LLM-мок, реранкер, проверка
  цитат в эвале — держали каждый свой ASCII-регэксп и не видели ни одного
  токена в кириллице: ретривал находил правильный чанк, а слой выше от него
  отказывался — уверенный неправильный ответ с кодом 200. Теперь все слои
  зовут общий `content_tokens()`, и что считать словом, решается в одном
  месте по построению.
- **Local-first:** приоритет выводится из источника прямо в схеме
  (`local=100`, `other=50`, `web=0`), при ранжировании твои данные стабильно
  выше веба при равной релевантности.
- **Лаборатория ретривала (`POST /v1/retrieve`):** тот же конвейер, что у
  `/v1/query` (`app/services/retrieval.py`: один эмбеддинг, одна выборка
  ног, ранжирование, реранкер), без синтеза и для двух вариантов настроек
  сразу — любое расхождение между ними вызвано только настройками. С
  `explain` каждый фрагмент несёт места и сырые скоры в обеих ногах, вклад
  каждой ноги (в сумме — итоговый скор), потолок скора для правила слияния,
  место после local-first и после реранкера. Отказ (404/409/429) решается
  до эмбеддинга; одинаковые списки реранкер оценивает один раз, разные —
  параллельно. Пока идёт реиндекс, оба маршрута ищут только по ключевым
  словам (`effective.mode: "keyword"`), а переопределение режима/слияния/
  весов в это время — 409, а не тихая подмена.
- **Папка-коннектор:** укажи `INGEST_WATCH_DIR` — всё, что падает в папку,
  оказывается в индексе в течение секунд; неизменённые файлы отсекаются по
  mtime+размеру ещё до чтения, симлинки отвергаются, мигнувший bind mount не
  сносит корпус, удаления файлов пропагируются в индекс.
- **Смена эмбеддера:** отпечаток векторного пространства хранится в базе;
  несовпадение на старте запускает пере-эмбеддинг всего корпуса под
  advisory-lock — сервис никогда не смешивает векторные пространства молча.
- **Конкурентный старт без гонок:** `CREATE EXTENSION IF NOT EXISTS` — это
  check-then-insert, и две реплики на свежем томе стабильно роняли одна
  другую (измерено: 10/10 запусков). Миграции идут под сессионным
  advisory-lock — общеплатформенным ключом, который держит и шлюз (все
  сервисы зонтичного стека смотрят в один Postgres), а инициализация пула
  проглатывает проигранную гонку расширения: раз проигравший её увидел,
  расширение победителя уже закоммичено.
- **Наблюдаемость:** входящий `X-Request-ID` эхом возвращается в ответе и
  пробрасывается в вызовы шлюза (эмбеддинги и синтез) — одно действие
  пользователя связывается в один id по журналам обоих сервисов (id не из
  печатного ASCII заменяется свежим: заголовок к шлюзу уходит в ASCII);
  `GET /metrics` отдаёт счётчики, которые сервис раньше вычислял и
  выбрасывал (см. таблицу API).
- **Расходы по функциям:** каждый вызов шлюза несёт заголовок
  `X-Attribution` — какая функция rag его сделала: `rag:embed-query`
  (эмбеддинг вопроса в `/v1/query` и `/v1/retrieve` — один на запрос при
  любом числе вариантов; во время реиндекса вопрос не эмбеддится и метки нет), `rag:embed-ingest` (`/v1/ingest`, `/v1/ingest/file` и
  проход вотчера), `rag:embed-reindex` (переэмбеддинг при смене эмбеддера и
  миграция ширины — из lifespan или CLI), `rag:rerank` (LLM-реранкер, в обоих маршрутах) и
  `rag:answer` (синтез ответа). Шлюз пишет метку в журнал `model_runs`, и
  расходы группируются по функциям. Метка называет функцию, никогда не
  пользователя; уходит только в шлюз; rag не пробрасывает чужую метку —
  цепочку между сервисами связывает `X-Request-ID`. Вне всякой функции
  заголовка нет вовсе. `tests/test_attribution_wire.py` валит любой запрос к
  шлюзу без метки и любой пишущий роут, не классифицированный по вызовам
  шлюза.
- **Журнал изменений настроек:** каждое изменение весов гибрида записывается
  в `rag_config_changes` (было → стало, sha256-дайджест ключа — никогда сам
  ключ, request id) в ОДНОЙ транзакции с записью самих весов: без записи в
  журнал изменения нет (503 `config_audit_unavailable`, ничего не изменено).
  Записи сериализуются между репликами транзакционным advisory-lock, а «было»
  читается из сохранённой пары, так что реплика с устаревшим кэшем пишет
  настоящий переход. Повтор того же значения — no-op: ни записи, ни события,
  но реплика подтягивает сохранённую пару. После записи в `platform:events`
  уходит факт `config_changed` (сервис + настройка, без значений) — открытые
  консоли обновляются сразу; публикация не ждёт Redis. `GET /v1/config/changes`
  листает журнал; без базы (memory-стор) журнал живёт в памяти процесса
  (`durable: false`, до 500 записей).

| `EMBED_BATCH_SIZE` | `64` | Текстов на вызов эмбеддера (кап запроса к удалённому эмбеддеру) — живой ingest (роут, аплоад, вотчер), пере-эмбеддинг и миграция ширины; ≥ 1 (0 валит старт) |
| `MAX_REQUEST_BYTES` | `10485760` | Кап тела HTTP-запроса — 413 до буферизации |
| `MAX_UPLOAD_BYTES` | `10485760` | Кап одного документа: и upload, и папка-коннектор. Ограничивает ПРОЧИТАННЫЕ байты, не работу разбора: pdf/docx сжаты, разбор ограничивают бюджеты в `app/services/extract.py` |
| `DB_POOL_MIN_SIZE` / `DB_POOL_MAX_SIZE` | `1` / `5` | Границы пула asyncpg на реплику |
| `INGEST_WATCH_DIR` | не задан | Папка-коннектор |
| `INGEST_WATCH_INTERVAL_S` | `5` | Период опроса папки |
| `JUDGE_BACKEND` | `mock` | Судья eval-харнесса: `mock` · `openai` |

Локальный Postgres из `docker-compose.yml` опубликован на `127.0.0.1:5433`,
а дефолт настроек — `5432`: рабочий DSN для сервиса и интеграционных тестов
рядом с поднятым compose — `postgresql://rag:rag@localhost:5433/rag`.

## Безопасность

Bearer с сравнением за постоянное время без досрочного выхода; найденный
контент попадает в промпт только внутри огороженного блока с защитой от
подделки ограждения (prompt-инъекция из отравленного чанка не может закрыть
рамку); лимиты размера на каждом уровне; ошибки провайдеров наружу — общий
502 без деталей топологии.

## Тесты и гейты

```bash
make test        # офлайн-набор; интеграционные с pgvector — при DATABASE_URL
make cov         # покрытие тем же набором, что make test: coverage/{run.json,coverage.json,junit.xml,html/}; только цифры, без порога
make cov-ci      # набор CI: то же + ярус pgvector на одноразовом контейнере (образ CI, случайный порт); НИКОГДА не направляйте DATABASE_URL на общий Postgres — PG-тесты пишут схему и строки прямо в эту базу
make lint && make typecheck
make format      # lint только проверяет; этот таргет пишет (ruff format + автофиксы)
make eval        # харнесс ретривала: hit_rate@k / recall@1 / MRR по каждой ноге
make lock        # после правки зависимостей: uv.lock (единственный артефакт — экспортов в репо нет)
```

Харнесс гоняет каждый из 42 вопросов золотого набора **тремя способами** —
только вектор, только ключевые слова, гибрид — и печатает сравнение. Корпус: 8
документов, три из них — намеренные «двойники» соседних тем, top_k = 3.

| нога | hit_rate@3 | recall@1 | MRR |
|---|---|---|---|
| vector | 0.83 | 0.71 | 0.766 |
| keyword | 0.86 | 0.74 | 0.794 |
| hybrid | 0.83 | 0.67 | 0.738 |
| _случайный retriever_ | 0.38 | 0.12 | — |

Случайная база (`min(1, top_k / n_documents)`) печатается рядом с каждой
цифрой намеренно: до 1.13.0 гейт стоял на `hit_rate@4 ≥ 0.8` при корпусе из 5
документов, то есть **ровно на уровне случайного угадывания**. Сейчас гейт —
`hit_rate@3 ≥ 0.75` при базе 0.38.

Вопросы размечены по категориям: `vector_only` (нулевое пересечение токенов с
целевым документом — ключевая нога обязана промахнуться), `keyword_only`
(редкий литерал вроде `ef_construction` или `429` внутри формулировки соседнего
документа — промахнуться обязана векторная), `distractor` (ровно один из двух
соседних документов) и `baseline`. Тест проверяет разметку на реальном прогоне,
а не на слово.

Оффлайн векторная нога — **мок** (`semantic` = рукописная таблица синонимов).
Цифры доказывают, что работает механика ранжирования, и ничего не говорят о
качестве продакшн-ретривала: для этого нужен `EMBEDDINGS_BACKEND=gateway`.
Отчётов два: `evals/report.md` пересобирается каждым `make eval`
(memory-store), а `evals/report_pgvector.md` — тот же харнесс с
`--store=pgvector` против живой базы, гоняется реже (в CI) и меряет тот
ранжировщик, который реально обслуживает трафик. CI также
гоняет promptfoo — живой red-team границы `/v1/query` по OWASP LLM01/LLM07.
Интеграционные тесты поднимают одноразовую базу на каждый тест и проверяют в
том числе, что план векторного запроса действительно использует HNSW-индекс.

Покрытие меряется по `app/` (строки и ветвления отдельно) и **намеренно без
порога**: сначала цифры. Публикуемая цифра — набор CI (`make cov-ci`): офлайн
`make cov` не видит SQL стора, и разница около 9 пунктов по строкам.
`coverage/run.json` пишется только после зелёного прогона: коммит, чистое ли
дерево до и после прогона и sha256 обоих отчётов — отчёт, переписанный
посторонним `pytest --cov` позже, со штампом уже не сходится. Итоговый `TOTAL`
в терминале — комбинированная цифра coverage.py (строки + ветвления); строки и
ветвления по отдельности — в `coverage/coverage.json`. CI гоняет тесты один раз
через `make cov` и выгружает `coverage/` артефактом `coverage-rag-pgvector` —
это подключено, но ещё не запускалось: джобы Actions не стартуют с 2026-08-14
(лимит расходов аккаунта).
